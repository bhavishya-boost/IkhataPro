# iKhataPro — Database Migration Plan
## localStorage → Supabase PostgreSQL

> **IMPORTANT:** This document is for FUTURE migration planning only.  
> DO NOT execute this migration in the current phase.  
> The existing iKhataPro application continues to use localStorage.

---

## Overview

iKhataPro Phase 1–9 operates on `localStorage` using the key `iKhataPro_app_state_v4`.  
This document outlines the safe, module-by-module plan to migrate to Supabase PostgreSQL when ready.

---

## Pre-Migration Requirements

Before starting migration:

- [ ] Supabase project is live and connected
- [ ] `MASTER_SCHEMA.sql` has been executed successfully  
- [ ] All RLS policies are verified via `SUPABASE_SECURITY_TESTS.md`
- [ ] A full JSON backup of all localStorage data has been exported
- [ ] The migration is tested on a staging copy of the application first
- [ ] All team members are informed of planned downtime window

---

## Migration Phases

### Phase M-1: Export & Backup

```
iKhataPro (Current)
    ↓
exportBusinessBackup() in state.js
    ↓
Download full JSON backup (iKhataPro_Backup_v4)
    ↓
Store backup file securely (offline + cloud)
```

**Steps:**
1. Open iKhataPro app
2. Go to Settings → Export Backup
3. Download JSON file for EACH business tenant
4. Verify JSON file is readable and complete
5. Store backup in at least 2 locations

---

### Phase M-2: Supabase Auth Setup

```
Create accounts for all business owners:
  - Owner registers with email/password via Supabase Auth
  - Profile row auto-created via trigger
  - business_members row created as OWNER
```

**Steps:**
1. Each business owner signs up via the iKhataPro login page (new Supabase auth flow)
2. Create their `businesses` row in Supabase
3. Insert their `business_members` row with `role = 'OWNER'`
4. Invite staff members (insert into `business_members` with appropriate role)

### Phase M-4: Migration Script Execution

```sql
-- Template for safe data insertion
-- Replace {business_uuid} with actual Supabase UUID

-- Step 1: Insert business data
INSERT INTO businesses (id, name, owner_name, ...)
VALUES ('{business_uuid}', '...', '...', ...);

-- Step 2: Insert business_members for owner
INSERT INTO business_members (user_id, business_id, role)
VALUES ('{owner_auth_uuid}', '{business_uuid}', 'OWNER');

-- Step 3: Insert customers (in batches of 100)
INSERT INTO customers (business_id, name, phone, balance, ...)
VALUES ('{business_uuid}', '...', '...', 0.00, ...);

-- Step 4: Insert transactions in chronological order
-- (important for balance reconstruction verification)

-- Step 5: Insert products

-- Step 6: Insert suppliers + supplier_transactions + purchases

-- Step 7: Insert invoices + invoice_items

-- Step 8: Insert pos_bills + pos_bill_items

-- Step 9: Insert expenses

-- Step 10: Insert employees

-- Step 11: Verify balance consistency
SELECT id, name, balance,
  (SELECT COALESCE(SUM(CASE WHEN type='GAVE' THEN amount ELSE -amount END), 0)
   FROM transactions WHERE customer_id = c.id AND is_deleted = false) AS computed_balance
FROM customers c
WHERE business_id = '{business_uuid}'
AND ABS(balance - (
  SELECT COALESCE(SUM(CASE WHEN type='GAVE' THEN amount ELSE -amount END), 0)
  FROM transactions WHERE customer_id = c.id AND is_deleted = false
)) > 0.01;
-- This query should return ZERO rows (all balances match computed values)
```

### Phase M-5: Verification & Reconciliation

For each migrated business, verify:

- [ ] **Customer count** matches: `SELECT COUNT(*) FROM customers WHERE business_id = '{id}'`
- [ ] **Transaction count** matches
- [ ] **Balance reconciliation** query returns 0 rows (see Phase M-4 Step 11)
- [ ] **Supplier payable total** matches: `SELECT SUM(balance) FROM suppliers WHERE business_id = '{id}'`
- [ ] **Product count** matches
- [ ] **Invoice totals** match
- [ ] **POS bill totals** match
- [ ] **Expense totals** match

### Phase M-6: Module-by-Module Application Migration

Replace localStorage calls one module at a time:

```
Priority Order:
1. Authentication (login/logout → Supabase Auth)
2. Businesses (tenant context)
3. Customers + Khata Transactions (core module)
4. POS Billing
5. Invoices & GST
6. Inventory & Products
7. Suppliers & Purchases
8. Expenses
9. P&L / Cash Flow / Reports
10. AI Copilot (query Supabase instead of localStorage state)
11. Notifications
12. Audit Logs
13. Backup/Restore
```

For each module, the migration pattern is:

```javascript
// BEFORE (localStorage via state.js)
const customers = window.iKhataStore.getCustomers();

// AFTER (Supabase)
const { data: customers, error } = await supabase
  .from('customers')
  .select('*')
  .eq('is_deleted', false)
  .order('name');
// RLS automatically enforces business_id scoping
```

### Phase M-7: Regression Testing

For each module after migration:

- [ ] Walk-in POS sale works correctly
- [ ] Credit POS sale creates Khata entry
- [ ] GAVE transaction increases customer balance
- [ ] GOT transaction decreases customer balance
- [ ] GST invoice calculates CGST+SGST correctly (INTRA)
- [ ] GST invoice calculates IGST correctly (INTER)
- [ ] Purchase updates supplier balance
- [ ] Supplier payment reduces balance
- [ ] Expense appears in P&L operating expenses
- [ ] Stock decreases on POS sale (inventory_movements logged)
- [ ] Stock increases on purchase
- [ ] Low stock alert triggers when stock ≤ min_stock
- [ ] Soft delete hides but preserves records
- [ ] Business switch only shows authorized business data
- [ ] Audit logs capture all mutations

---

### Phase M-8: localStorage Deprecation

Only after ALL modules are verified:

1. Remove `localStorage.setItem()` calls from state.js
2. Keep `localStorage.getItem()` temporarily for rollback safety
3. After 30-day stability period, remove all localStorage dependencies
4. Archive the `iKhataPro_app_state_v4` key reference

---

## Rollback Plan

If migration fails at any point:

1. The localStorage data is untouched (we never delete it during migration)
2. Switch `SUPABASE_ENABLED` flag to `false` in config
3. Application falls back to localStorage instantly
4. Investigate issue, fix, and retry migration

---

## AI Copilot Isolation Requirement

After migration, the AI Copilot (`intelligence.js`) must ONLY query:

```javascript
// The RLS context automatically scopes all queries to the current business
const { data } = await supabase.from('transactions').select('*');
// Returns ONLY the current user's business transactions — AI cannot see others
```

The AI must NEVER receive data from another business. Supabase RLS enforces this at the database level.

---

## Backup Isolation Requirement

Future backup/export via Supabase must:

1. Call `exportBusinessBackup()` adapted to fetch from Supabase
2. The query automatically returns only authorized business data (RLS)
3. Export format matches the existing JSON backup format for continuity
